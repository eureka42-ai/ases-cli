# ADR-0018: Portabilidade verificada no Windows (Credential Manager, DACL, caminhos) e matriz de suporte

- **Status:** ACCEPTED (aprovado pelo responsável em 24/11/2026).
- **Tarefas:** TAR-0065..TAR-0069
- **Requisitos:** AER-REQ-122, 225, 227, 229, 230, 233, 234, 238, 239

## Decisão
1. **SecretStore no Windows** (`createWindowsCredentialStore`): é o Credential Manager do usuário (blob protegido por DPAPI), via `CredWriteW`/`CredReadW`/`CredDeleteW` do `advapi32`.
   - **Como é chamado:** P/Invoke compilado pelo `Add-Type` do **Windows PowerShell 5.1 do sistema**, pelo caminho absoluto `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe`, sem passar pelo PATH. Isso não adiciona dependência nem binário nativo.
   - **O que fica fora do argv:** o script inteiro, com alvo e valor, vai pelo **stdin** em base64. O argv só tem flags fixas (`-NoLogo -NoProfile -NonInteractive -Command -`), então nem o valor nem o keyId aparecem na lista de processos.
   - **Formato do alvo:** `eureka42.aer/<keyId>`, do tipo `CRED_TYPE_GENERIC` e com persistência `LOCAL_MACHINE` (do usuário, nesta máquina).
   - **Sem PowerShell:** o cofre fica indisponível. Nunca cai para arquivo.
2. **DACL dos diretórios privados** (runtime do IPC, com o arquivo de tokens, e `.ases/db`):
   - O AER lê as regras **por SID**, pela API .NET (`DirectoryInfo.GetAccessControl`), o que não depende do idioma do Windows.
   - Só podem ter acesso o usuário atual, o SYSTEM (`S-1-5-18`) e os Administradores (`S-1-5-32-544`). Se houver qualquer outro SID, o AER restringe com `icacls /inheritance:r` e as concessões explícitas, e confere de novo. Se ainda sobrar, falha com `INSECURE_PATH`.
   - Junction ou symlink no lugar do diretório também falha.
   - O script usa só .NET, sem cmdlet de módulo. Chamado de dentro do pwsh 7, o 5.1 herda o `PSModulePath` do 7, e o `Get-Acl` falhava ao carregar (CI run 45408100121). Tirar o `PSModulePath` travou o PowerShell no windows-11-arm (run 45409051065), então o ambiente segue herdado.
3. **Named Pipe** (AER-REQ-227): o Node não permite definir a DACL do pipe. A autenticação continua sendo pelos tokens `control`/`monitor` do arquivo de sessão.
   - Esse arquivo fica no diretório de runtime, que agora tem DACL **verificada**. Então só o usuário (e SYSTEM/Administradores) consegue ler o token, e sem token o engine recusa a conexão.
   - O nome do pipe inclui o hash do usuário e do projeto.
4. **Caminhos** (AER-REQ-230): o projeto é identificado pelo `projectId` do manifesto, não pelo caminho.
   - **e2e Windows:** o mesmo projeto aberto por letra de unidade, UNC (`\\localhost\C$\…`), junction e `subst` tem um só `projectId` e um só banco.
   - **Não testado:** compartilhamento SMB remoto. SQLite em rede não é recomendado.
5. **Matriz de suporte** (AER-REQ-225/233/239): o job `support-matrix` do CI gera, a partir dos jobs **reais** do run, o estado de cada alvo: PASS, FAIL ou NOT_RUN.
   - Cancelado ou na fila conta como NOT_RUN.
   - Os alvos arm64 de Windows/Linux são CONDITIONAL e não são anunciados como suportados sem decisão do responsável.
   - O mesmo script roda local com `gh`: `node scripts/support-matrix.mjs <run-id>`.
6. **TUI no ConPTY/Windows Terminal** (AER-REQ-234): **PASS no CI** desde a TAR-0070 (PHASE-16). O `node-pty@1.1.0`, aprovado pelo responsável, é instalado só no CI do Windows (`--no-save`) e fica fora do pacote.
   - **Alvos arm64:** Windows e Linux arm64 passam de CONDITIONAL para TARGET (24/11/2026).

## Consequências
- **Custo:** cada operação de segredo no Windows custa um processo PowerShell mais a compilação do `Add-Type` (cerca de 1 a 8 s no CI). A checagem de DACL roda uma vez por diretório e por processo.
- **Constrained Language Mode:** em máquinas com esse modo (AppLocker/WDAC), o `Add-Type` é bloqueado. Nesse caso o cofre aparece como indisponível no `doctor`, e a DACL não pode ser lida, então o AER falha fechado com `INSECURE_PATH`.
