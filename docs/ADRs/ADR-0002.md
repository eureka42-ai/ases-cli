# ADR-0002 — SQLite como autoridade, espelho JSONL e driver `node:sqlite`

- **Status:** ACCEPTED, com reavaliação obrigatória antes do release estável (PHASE-12/15)
- **Tarefas:** TAR-0006, TAR-0007, TAR-0009
- **Requisitos:** AER-REQ-018, 061–069, 236

## Contexto

O §6.1 exige SQLite transacional como fonte da verdade e `HISTORY.jsonl` como espelho derivado. O §3.6 pede um driver que rode em macOS, Windows e Linux sem `--experimental-*` forçado e sem módulo exclusivo de Mac.

Opções avaliadas em 22/11/2026, no host macOS arm64 com Node 22.19.0:

| Opção | Prós | Contras |
|---|---|---|
| `node:sqlite` (embutido) | zero dependências; binário vem com o Node em todos os SO e arquiteturas; sem install scripts; SQLite 3.50.4 com JSON1; sem flag desde o Node 22.13 | API marcada como *experimental* (emite `ExperimentalWarning`); sem `backup()` no Node 22 |
| `better-sqlite3` | API madura, muito usada | addon nativo: precisa de prebuild por SO/arquitetura e de install script (conflita com `ignore-scripts=true`, §9.6); risco de supply chain |
| `sqlite3` / wasm | — | assíncrono/callback, ou sem acesso a arquivo com locks reais entre processos |

## Decisão

1. **Driver `node:sqlite`** (`DatabaseSync`), importado **apenas** em `packages/persistence`. O lint de fronteiras faz isso valer, e a troca futura de driver fica confinada a esse pacote.
2. O `ExperimentalWarning` específico do SQLite é suprimido no carregamento do módulo, para não sujar a TUI nem o stdout JSON. Qualquer outro aviso continua sendo emitido.
3. **Pragmas:**
   - `foreign_keys=ON`, `busy_timeout=5000`.
   - `journal_mode=WAL` em arquivo. O modo efetivo é lido de volta; se o filesystem não aceitar WAL, o modo real é exposto ao chamador em vez de ser presumido.
4. **Escritas** em `BEGIN IMMEDIATE`, para que dois processos nunca tentem promover um lock de leitura e travem. A transição de estado e o evento correspondente são gravados na **mesma transação**.
5. **Migrações** versionadas via `PRAGMA user_version`. Antes de migrar um banco já existente, é feito um backup com `VACUUM INTO`, verificado com `integrity_check` e `user_version`. Banco com versão mais nova que o código: erro `DB_SCHEMA_TOO_NEW`, sem tocar no arquivo. Não existe downgrade.
6. **Eventos imutáveis:** triggers abortam `UPDATE`/`DELETE` em `events`. O `eventId` é `UNIQUE`; repetir o mesmo evento não altera nada, e repetir um `eventId` com payload diferente é erro.
7. **Hash do payload:** `sha256` da serialização canônica (chaves ordenadas), igual à do `scripts/ases-dev.mjs`. Assim o histórico interino da PHASE-01 é verificável pelo mesmo algoritmo e importável como seed quando o engine assumir a escrita, o que acontece na PHASE-03.

## Consequências e riscos

- **R:** `node:sqlite` pode mudar de API entre versões do Node. **Mitigação:** `engines` fixado, matriz de CI por versão do Node e uso confinado a um pacote.
- **R:** a supressão do aviso esconde o fato de a API ser experimental. **Mitigação:** este ADR e o `ases doctor` (PHASE-03) informam o estado.
- Permissões do arquivo do banco (`0600`/DACL) ficam a cargo do engine via `PlatformAdapter`, ao criar `.ases/db/` (PHASE-03, AER-REQ-014/202).
- **Gate de reavaliação:** antes de `STABLE_MULTIPLATFORM`, rodar a suíte multiprocesso em Windows e Linux reais. Se `node:sqlite` falhar lá, trocar o driver por novo ADR.
- O pacote `event-log` sugerido no §3.2 foi incorporado a `persistence`, porque append, replay e verificação compartilham a mesma transação. Separar quando a redação de segredos entrar no pipeline de eventos (PHASE-10), se houver motivo concreto.
