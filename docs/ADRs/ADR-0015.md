# ADR-0015: Policy engine, approvals por hash, registry de extensões e SecretStore nativo

- **Status:** PROPOSED (PHASE-10, 23/11/2026). Aguarda revisão humana.
- **Tarefas:** TAR-0048..TAR-0053
- **Requisitos:** AER-REQ-131..140, 161..175, 229

## Decisão
1. **Policy engine** (`@aer/security/policy`):
   - **Escopos:** os 17 do §12.3. Escopo não classificado → `DENY` (AER-REQ-161).
   - **Política padrão V1:**
     - `READ_REPO` e `WRITE_TASK_WORKTREE` sem pergunta;
     - `RUN_PRIVILEGED` sempre negado;
     - o resto só com aprovação.
   - **Camadas** (global ∩ projeto ∩ tarefa) se combinam por interseção: nenhuma concede mais que a mais restritiva.
   - **Aprovação** (AER-REQ-162/173) vale só para o hash canônico da operação exata (escopo + sujeito + detalhe, p.ex. o SHA-256 do manifesto). Ela:
     - tem validade (padrão 60 min, máx. 24 h);
     - é **de uso único** (`CONSUMED`);
     - não se transfere de uma tarefa para outra.
   - Mudar um byte do manifesto exige aprovação nova.
2. **Registry de extensões** (migração v4; §9.6):
   - **Máquina de estados:** `DISCOVERED → INSPECTED → APPROVED → INSTALLED → VERIFIED | FAILED | REJECTED`.
   - **UNSAFE nunca chega a APPROVED.** A regra fica no store e também no comando.
   - **Update** (manifesto com outro hash): a extensão volta a `INSPECTED` e não é reativada sozinha (AER-REQ-138).
   - **Skills** (`.claude/skills`, `.agents/skills`, do projeto e do usuário):
     - o front matter aceita só `chave: valor`; âncoras, tags e multilinha são recusadas como inválidas e nunca interpretadas (AER-REQ-132);
     - a importação é por **referência** verificada por hash, sem copiar nem alterar o original.
   - **MCP** (`.mcp.json` do projeto; plugins via `claude plugin list --json`):
     - o AER guarda só os nomes das variáveis, nunca os valores;
     - marca rede, `npx`/`uvx` e credenciais;
     - o health check `initialize` + `tools/list` roda sob timeout, com a árvore de processos encerrada no fim;
     - as ferramentas ficam no namespace `mcp::<id>::<tool>` (AER-REQ-135/136).
   - **Plugins Claude** (AER-REQ-134):
     - listagem e instalação **só** pelo CLI oficial (`claude plugin list --json`, `claude plugin install <id> --json -s project`);
     - **nunca** `-y` nem `--accept-command`: um comando declarado pelo marketplace volta para o humano confirmar no próprio Claude;
     - nada é escrito nos diretórios do Claude.
   - **Scanner de supply chain** (AER-REQ-139/168): scripts `pre/post/install/prepare`, `curl|wget … | sh`, `base64 -d | sh`, download-and-execute em PowerShell, `eval(atob(…))`, `rm -rf /`, leitura de credenciais de outras ferramentas, binários ELF/Mach-O/PE e symlink que escapa (nunca seguido).
     - **Veredito:** HIGH → `UNSAFE`; MEDIUM → `REVIEW`; o resto → `SAFE`.
3. **Compatibilidade por provider** (§9.1, AER-REQ-133/140):
   - Plugin com hooks, commands, agents, LSP ou MCP fica `CLAUDE_ONLY` nos demais; sem nada disso, `UNKNOWN`. **UNKNOWN nunca vira suportado.**
   - O **worker** só inicia uma tarefa com `--ext` se cada extensão estiver `VERIFIED` e `canUse(compat, provider)`. Caso contrário, a tarefa vai para `BLOCKED EXTENSION_INCOMPATIBLE`/`EXTENSION_NOT_VERIFIED` antes de qualquer processo.
4. **SecretStore nativo** (AER-REQ-229, §12.2 item 8):
   - **macOS:** Keychain via `/usr/bin/security -i`. Os comandos vão **pelo stdin**, então nem a chave nem o valor aparecem no `ps`.
     - O valor é gravado já em hex, porque o `-w` devolve hex quando o valor tem byte não ASCII (verificado em 23/11/2026). Gravar hex deixa a leitura inequívoca.
   - **Linux:** `secret-tool` (libsecret), com o valor pelo stdin. Exige sessão D-Bus.
   - **Windows:** **indisponível de propósito**. O `cmdkey` expõe o segredo no argv; o binding nativo fica para a PHASE-15.
   - **Nunca cai para arquivo plaintext.** O CLI `ases secret set|has|delete|status` lê o valor do stdin (sem eco no TTY) e nunca o imprime.

## Consequências e limites
- **Extensões ainda não são carregadas nas sessões dos providers:** o claude roda com `--strict-mcp-config`, o ACP com `mcpServers: []`. Esta fase entrega o registry, a inspeção, a aprovação e a **trava** de compatibilidade; carregar uma extensão VERIFIED dentro da sessão fica para depois.
- **Credenciais do MCP não são repassadas:** o health check sobe o servidor **sem** as variáveis declaradas no `.mcp.json`, para o segredo não sair do arquivo. Um servidor que precise de token aparece como FAILED. Repassar credenciais exigiria um approval `ACCESS_SECRETS` + SecretStore, não implementado.
- **Health check:** só `stdio`. HTTP/SSE são inspecionados, mas não iniciados.
- **Hooks do AER (§9.5):** não implementados nesta fase.
- **Pedidos de permissão do agente** (ACP `execute` etc.) continuam negados pela política fixa do adapter. A integração com `/approval` em tempo real, que exigiria pausar a tarefa, fica para depois.
